## Chatbot vs. Agente de Larga Duración 

- Un chatbot es pasivo y sin estado: solo responde cuando se le pregunta ‣ 

- Un agente de larga duración es fundamentalmente diferente: ‣ ‣ 

   - Multi-sesión: puede correr por semanas, meses o años 

   - Dormante: se activa solo cuando ocurre un evento (webhook, aprobación humana, temporizador, etc.) 

   - Complejo: la unidad de trabajo y su complejidad crecen con el tiempo 

## Características Clave de un Agente de Larga Duración 

- Event-driven: necesita una señal de "wake up" para activarse ‣ 

- Durabilidad: mantiene memoria persistente con checkpoints temporales ‣ 

- Recuperación ante fallos: debe poder retomar desde donde se quedó ‣ 

- Desafíos principales identificados: ‣ ‣ ‣ ‣ 

   - Degradación de calidad de LLM con contextos muy largos 

   - Deriva no estructurada (el agente hace cosas inesperadas) 

   - Staleness de snapshots (datos desactualizados enviados al agente)

## Gestión de Memoria en ADK 

- ADK soporta varios tipos de memoria con distintos ciclos de vida: ‣ ‣ ‣ ‣ ‣ 

- ‣ 

   - Temporal (invocación): dura solo una interacción; desaparece al terminar 

   - Sesión: persiste durante una sesión completa (similar a sesiones web) 

   - Usuario (prefijo `user:` ): persiste indefinidamente asociada al usuario (ej. preferencias como "Sam no hace noches de semana") 

   - Artefactos: archivos, videos, audios u outputs temporales generados por el agente; soporta almacenamiento en memoria, archivos locales o GCS ‣ 

   - Memoria a largo plazo: búsqueda semántica desde una base persistente LRAG, Memory Bank, in-memory) ‣ ‣ 

- En la demo se implementó una memoria personalizada en formato Markdown como extensión de las 3 opciones nativas de ADK ‣ ‣ 

- Sesión demo con "Sam": el agente recordó la preferencia entre sesiones usando el prefijo de usuario ‣ ‣ 

- El seat map del evento se guardó como artefacto para no recargarlo en cada interacción ‣ ‣

## Sub-agentes para Aislamiento de Contexto 

- Usar sub-agentes permite separar contextos y reducir tokens enviados al LLM ‣ ‣ ‣ 

- En la demo: un agente principal maneja la búsqueda de conciertos; un subagente separado maneja el presupuesto ‣ 

- Menos contexto = menos alucinaciones y menor costo ‣ 

- Para mantener control en el agente raíz, se llama al sub-agente como tool (no como handoff completo) ‣ ‣ 

## Invocación y Arquitectura de Triggers 

- El agente necesita un punto de invocación para ser activado externamente ‣ 

- Opciones: CronJob, HTTP server, PubSub, webhooks ‣ 

- En la demo: se construyó un HTTP server (runner/servidor) que recibe POST requests y despierta al agente ‣ ‣ 

- El runner conecta el agente con sus servicios de sesión, artefactos y memoria ‣ ‣ ‣ 

- Un worker/scheduler LCronJob) hace POST al servidor periódicamente ‣ ‣ 

## Resumibilidad ante Fallos 

- Problema: al reiniciar el proceso, el agente repite todo desde cero (rejoins queue, etc.) ‣ 

- Solución: marcar funciones de larga duración como `long_running_tool` y habilitar `resumability=true` en la configuración ‣ ‣ ‣ 

- Efecto: al reanudar, el agente sabe dónde estaba en el proceso sin repetir pasos costosos ‣

## Interceptores / Callbacks 

- ADK ofrece callbacks ( `before_tool_call` ) que permiten modificar prompts, contexto o inputs antes de llamar a tools o modelos ‣ ‣ 

- Caso de uso en la demo: verificar y refrescar el mapa de asientos justo antes de ejecutar la compra, evitando comprar algo agotado ‣ 

- Son el "punto de hacking" del ADK para manipular el flujo del agente ‣ 

## Workflows Deterministas con Grafos 

- Para evitar deriva no estructurada, se puede predefinar el flujo de trabajo como un grafo en ADK ‣ ‣ 

- Nodos: unidades de ejecución (agentes, funciones, tools) 

- Aristas: conexiones entre nodos que definen el flujo Ventajas: ‣ ‣ 

   - Control total sobre qué tools/agentes son accesibles en cada etapa Flujo determinista para tareas predecibles 

- El workflow de la demo incluye un punto de pausa para input humano (confirmación de presupuesto) y un loop de verificación de la cola ‣ ‣ ‣ ‣
